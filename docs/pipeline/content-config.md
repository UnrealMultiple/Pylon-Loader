# 内容管线：配置（Config）

## 1. 职责

把作者用 `ModConfig.Toggle/Range/Radio/Dropdown/Cycle/Color/Header/Button/Link` 声明出来的选项，变成**能读、能改、能落盘、能回滚**的一份配置。

| 环节 | 做什么 |
|---|---|
| 注册 | 读作者的静态 `Options` 字典 → 建成 `ModConfigOption` 列表 → 校验声明 |
| 读盘 | 默认值打底，再按 JSON 里存的值逐项覆盖（单项坏掉只丢那一项） |
| 编辑 | 草稿（draft）隔离：屏幕只碰草稿，按"应用"才写回真值 |
| 应用 | 逐项比较 → 写回 → `OnChanged(key)` → `OnApply()` → 落盘 |
| 撤销 / 恢复默认 | 丢草稿 / 用声明里的默认值重填 |
| 按钮与链接 | `Button` 调作者方法或委托；`Link` 用浏览器打开 |

**已接**：服务端配置同步（`ConfigScope.ServerSide`）——连上收服务器的值、改了发请求由服务器裁决、离开世界写回本机值，见 2.6。

**不接**：配置的自动重载（`NeedsReload` 那套快照）、跨 mod 的配置依赖。

## 2. 我们的设计

### 2.1 文件

```
Pipelines/Config/
  ConfigPipeline.cs    模块：注册、读盘、草稿、应用、落盘、按钮动作
  ConfigEntry.cs       公开：一份配置的注册记录（草稿与文件路径在这一层）
  ModConfigLoader.cs   公开门面：作者已编译的静态 API，只转发
```

### 2.2 选项从"声明"来，全程零反射

与参考实现不同，我们没有"反射字段当选项"这一步。作者重写虚方法：

```csharp
protected override void DeclareOptions(ConfigOptions options) =>
    options.Add("Power", Range(10, 0, 100))
           .Add("FastMode", Toggle(true))
           .Add("OpenWiki", Link("https://..."));
```

于是整条管线**一处反射都没有**：

* 声明顺序 = 代码顺序（不随编译器重排，也不用 `MetadataToken` 排序）；
* 键名、标签、校验、默认值在注册期一次性定死；
* 声明写错（键为空、重名、Range 的 `step <= 0`、Dropdown 超过 12 项）在注册期就报出来，而不是等 UI 画不出来；
* `Button` 的动作是**委托**（`Button(cfg => cfg.Apply())`），不是方法名字符串——按名字找方法同样要反射，而且拼错只会在点下去那一刻静默失败。

草稿也不克隆对象：屏幕的改动写进一张 `键 → 值` 的待提交表，`ModConfig.GetValue` 先看这张表。旧做法用 `Activator.CreateInstance` 造一份克隆，那是一次反射 + 一次完整对象复制。

### 2.3 值：一个字典 + 逐项校验

`ModConfig` 用 `Dictionary<string, object>` 存值，写入一定经过 `Valid`/`Snap`：

* `Range`：先夹到 `[Min, Max]`，再按 `Step` 对齐（对齐后可能超出上界，再夹一次）；
* `Radio/Dropdown/Cycle`：不在 `Choices` 里就拒绝；
* `Color`：`#RRGGBB`；
* `Toggle`：布尔。

**拒绝而不是"夹到合法值"**（Range 除外）：作者把 `Cycle` 改成 `"A"` 而合法值是 `["B","C"]` 时，静默改成 `"B"` 会让作者以为自己的赋值生效了。

### 2.4 草稿隔离

`Begin()` 为每份配置克隆一份草稿；`View(entry)` 返回草稿（没有就返回真值）。三条不变量：

1. 屏幕**只**碰草稿，因此"改了又不想保存"永远可以无副作用地丢弃；
2. `Apply()` 是唯一把草稿写回真值的入口，写回顺序是"逐项比较 → 只对变了的项发 `OnChanged`"；
3. 世界内的 `SetOption` **不走草稿**，立刻生效并落盘——作者在游戏逻辑里改配置不该被 UI 的草稿状态影响。

### 2.5 落盘

一份配置一个文件：`{存档目录}/ModConfigs/{Mod名}_{配置名}.json`，内容是 `键 → 值` 的扁平对象。

* 只用扁平结构：值都是标量（bool/double/string），嵌套没有意义；
* 写失败**不抛**给作者：记一条日志，游戏继续；
* 读失败（文件坏了）**整份退回默认值**并记一条，而不是抛——一次坏文件不该让 mod 加载不了。

### 2.6 服务端配置（`ConfigScope.ServerSide`）

作者的配置类多写一个 `public override ConfigScope Scope => ConfigScope.ServerSide;` 就归服务器管。管线做四件事：

| 时机 | 做什么 |
|---|---|
| 服务器把世界数据发给某客户端（原版消息 7） | 把每份 `ServerSide` 配置的「键 → 值」推给这个客户端 |
| 客户端收到 | 记下本机原值（每份只记第一次）→ 写值 → `OnApply()` |
| 客户端改值（`Apply`） | 先本地生效，再把整份值当**请求**发给服务器 |
| 服务器收请求 | 调作者的 `AcceptClientChanges(from, requested, ref message)`：过了就存盘 + 更新 + 回信；没过就只回信（原因给客户端看） |
| 客户端离开世界 | 把服务器改过的值**写回本机原值**（否则服务器上的值会留在自己的单机存档里） |

**为什么搭原版消息 7 的车**：新客户端连上时服务器必然会发世界数据，这是「这个客户端现在要开始收东西了」的唯一可靠信号；自己造一个握手包要在两条连接状态机上都加状态。

**为什么客户端改值先本地生效**：等服务器回信再生效会让滑杆来回跳；服务器拒绝时下一次同步/回信会把值掰回来。

**为什么载荷是「键名 + 值」平铺**：值本来就都是标量，走现成的 `NetCodec` 就够，不需要第二套打包格式；收到的每一项仍然过一遍 `Coerce`（对端可能是别的版本）。

**作者钩子**：`AcceptClientChanges(int fromPlayer, Dictionary<string, object> requested, ref string message)`——默认全接受；把不想接受的键从 `requested` 里删掉就是**部分接受**，返回 false 是全部拒绝，抛异常按全拒绝处理。

## 3. 取舍理由

* **为什么不像参考实现那样克隆一份"载入期快照"？** 那套是为了回答"这个改动需不需要重载世界"。我们的配置没有 `NeedsReload` 这个契约（作者的 `OnChanged` 自己决定怎么响应），多存一份快照就是多一份要同步的真相。
* **为什么 `Apply` 要"逐项比较"而不是"全量发 `OnChanged`"？** 作者的 `OnChanged` 经常做重活（重算 Buff 表、重发贴图）；没变的项也发一遍会让"应用"明显卡顿。
* **为什么 `Reset` 与 `Defaults` 是两个方法？** `Reset` 是"立刻把真值恢复默认并落盘"（给代码用），`Defaults` 是"把草稿填成默认"（给屏幕的"恢复默认"按钮用）；后者不该有副作用。
* **为什么 `Button` 的动作按方法名反射？** 声明是静态字段，拿不到实例；方法名让作者既能在静态声明里指定动作，又能让动作落在配置实例上。

## 4. 失败语义

| 情况 | 行为 |
|---|---|
| `Options` 没声明 | 注册失败并说明原因（不是空配置静默通过） |
| 键名为空 / 重名 | 注册期抛，指名到选项 |
| `Range` 的 `step <= 0` | 注册期抛 |
| `Dropdown` 超过 12 项 | 注册期抛（游戏的下拉只有 12 格） |
| 存盘值类型不对 | 那一项退回默认值，记一条警告 |
| 存盘文件损坏 | 整份用默认值，记一条错误 |
| `EnabledWhen` 谓词抛错 | 记一条，这一行按"可用"处理 |
| `Button` 方法找不到 | 记一条，点了什么也不发生 |
| 写盘失败 | 记一条，内存里的值仍然生效 |
| `AcceptClientChanges` 抛错 | 按"全部拒绝"处理，回信说明 |
| 同步包里的键在本机不存在 / 值不合法 | 那一项跳过（对端可能是别的版本） |
| 离开世界时写回失败 | 记一条；下一次进服务器会重新记原值 |

## 5. 扩展方式

新增一种控件：`OptionKind` 加一项 → `ModConfig` 加一个工厂 → `ConfigPipeline.Valid/Snap` 加一个分支 → UI 加一条绘制分支。值仍是标量，落盘格式不变。

## 6. 与其它管线的边界

* **安装管线**：配置注册发生在内容注册期（`ModType` 发现之后、`PostSetupContent` 之前）。
* **UI 管线**：屏幕、布局、控件绘制全在 `UI/ModConfigMenu*`；本管线只提供"值 + 事务"。
* **网络管线**：`ServerSide` 配置同步借网络管线的子通道（`ConfigNetPipeline`），不新开消息号；长度上限与收包兜底都复用现成那套。
* **键位 / 触屏按钮**：按钮布局不在配置里（由游戏自己保存），两者互不依赖。
