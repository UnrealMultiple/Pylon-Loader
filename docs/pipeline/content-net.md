# 内容管线：网络（Net）

## 1. 职责

自建一条"Mod 数据"通道：把 `ModPacket`、`Mod.NetSend/NetReceive`、实体的 `SendExtraAI/ReceiveExtraAI`、全局对象的 `NetSend/NetReceive` 打包成带类型标记的二进制流，走游戏自己的 NetModule 消息。

| 游戏时机 | 做什么 |
|---|---|
| `NetManager.Read` | 拦住我们的消息号 → 按标记分派（Mod 包 / 世界数据 / NPC 附加数据 / 弹幕附加数据） |
| `NetMessage.SendData` | 每个 mod 的 `HijackSendData` 可否决原版发送；原版之后按消息号补发我们的数据（7 = 世界、23 = NPC、27 = 弹幕） |
| 安装期 | 建立"名称 → Mod"与"全局类型 → 编号"两张表 |

**不接**：数据包压缩、加密、重传；这些是游戏 NetModule 的职责。

## 2. 我们的设计

### 2.1 文件

```
Pipelines/Net/
  NetPipeline.cs   模块：两个游戏入口 + 四种包的收发
  NetCodec.cs      值序列化（标记表）、名称/编号表
```

### 2.2 通道：一个消息号 + 一个种类字节

消息号固定（`0xB17E`），首字节是种类，其次才是载荷。**先判种类再读内容**：

`KindPacket`（Mod 包）→ 名称 + 值序列；`KindWorld` → 名称 + 值序列；`KindNpc` / `KindProjectile` → 实体定位键 + 本体值序列 + 若干全局对象的值序列。

### 2.3 三条改进（相对旧实现）

1. **全局对象用编号而不是类名**。旧实现把 `GetType().Name` 字符串写进每个包，接收端再逐个字符串比对；一帧几十个弹幕时这是纯浪费。现在安装期建一次"全局类型 → 编号"表，包体只有一个 `byte`/序号，接收端直接按编号取。
2. **名称定位用字典**。`名称 → Mod` 建一次；旧实现每包一次 `ModLoader.TryGetMod`（内部是线性扫描）。
3. **发送侧复用缓冲**。`MemoryStream` + `BinaryWriter` + 最终 `byte[]` 旧实现每次发包分配三份；弹幕附加数据是"每帧每弹幕"级别的调用。现在复用一个池化缓冲，写完直接交给 `NetPacket`。

### 2.4 包大小

硬上限 65000 字节：超过就丢并只报一次（`Safe.Once`）。不静默截断——截断的包在对端会读出错位的数据，比丢包更难查。

### 2.5 值序列化

一张固定的标记表（空值/整数族/浮点/布尔/字符串/布尔数组/二维向量），未知类型退化成 `ToString()` 当字符串发。接收端遇到未知标记返回 `null`，让上层按"缺值"处理——这样两侧协议版本不一致时是"少一个值"，而不是"整包错位"。

## 3. 取舍理由

* **为什么不按每个 mod 一条消息号？** 消息号是全局资源；mod 数量不可预知，动态分配会和游戏的消息号空间打架。固定一个号 + 种类字节 + mod 名，是唯一不需要和内核协商的方案。
* **为什么 NPC / 弹幕要单独两种包？** 它们的接收端需要"先找到实体"（NPC 按 index+type，弹幕按 owner+spawner+index+generation）；用定位键而不是引用，才能在乱序/丢包后仍然自洽。
* **为什么弹幕定位键是四元组？** 弹幕会被回收复用；`owner + key.Spawner + key.Index + key.Generation` 是唯一能区分"同一槽位的新旧弹幕"的组合。只按 index 会把数据写到复用过槽位的新弹幕上。
* **为什么 `HijackSendData` 放发送入口而不是别处？** 它是作者唯一能"替游戏决定这条消息发不发"的位置；放在 `SendData` 之前，作者可以拦下任何一条原生消息。

## 4. 失败语义

| 情况 | 行为 |
|---|---|
| 载荷超过 65000 字节 | 丢弃，只报一次 |
| Mod 名找不到 | 丢弃（对端少装了 mod，不是错误） |
| 接收某个全局对象抛错 | 记一条，继续下一个全局对象 |
| 物品附属包对不上号（编号指向另一件 mod 物品） | 丢弃这一条，只报一次；贴错物品比不同步更难查 |
| 附属包在原版物品包之前没到 | 过期（10 秒）后丢弃 |
| NPC / 弹幕定位失败 | 丢弃这一包 |
| 值序列化遇到未知标记 | 读成 `null`，由上层按缺值处理 |
| `HandlePacket` 抛错 | 记一条，不影响其它包 |
| 整个包解析抛错 | 记一条，**不**再交回原版（半读的流已经不可用） |

### 4.0 内容指纹（联机一致性）

配方 / 商店 / 掉落这些管线的编号都按「安装顺序」发号，两端 mod 集合或顺序不同就整片错位，而且错得无声。`ContentFingerprint` 在注册完成时把「种类 + 编号 + Mod名/类型名」按顺序折成一个 64 位哈希：

* 启动时记一条日志（有多少内容、指纹多少）；
* 服务器发世界数据（消息 7）时随包把指纹发给他；
* 客户端收到后比对，不一致就记一条错（带两端的十六进制值），再把自己的指纹回给服务器——两侧日志都能对上号；
* 只报错不断连接：玩家至少能从日志知道是哪一侧 mod 装错了，断不断由人判断。

指纹不参与任何游戏逻辑；哈希用 FNV-1a，只为了「发现不同」，不抗碰撞。

### 4.1 物品附属数据（通道种类 5）

原版物品包（5 = 玩家装备 / 背包槽，21 = 地上物品）只带「编号 / 堆叠 / 前缀」，作者写在 `ModItem.NetSend` 里的字段过不了网。做法：

1. **发送侧**：`NetMessage.SendData` 里，物品包在调原版之前先补一条附属包（`ItemSync.BeforeSend`）。顺序不能反——接收侧是「等原版把物品摆好再贴」，晚到就贴不上。没重写 `NetSend` 的普通物品一个字节都不发。
2. **包体**：包号 + 位置（物品索引 / 玩家索引 + 槽号）+ 物品键（`Mod名/类型名`）+ 本体值序列 + 若干全局对象值序列（按全局注册表里的编号，不写类名字符串）。
3. **接收侧**：挂在 `MessageBuffer.ProcessData` 上，先从包头取包号与位置，去待贴队列里找最早的一条，**原版处理完**再把附属数据贴到槽里那件物品上（那时物品才刚换成新的那件）。
4. **校验**：贴之前比对物品键；对端编号指向另一件 mod 物品说明两端装载顺序不一致，丢掉这一条并只报一次。
5. **进世界补发**：客户端进世界头 60 帧里原版会重发自己的背包，此时对端物品表还没铺好；这些槽号记下来，60 帧后按 `NetMessage.SendData(5, …)` 重发一次。

箱子（32）：**结构上查证过**——本构建的 `Chest` 存的是 `ChestItem` 结构体，只有 `type / stack / prefix / favorited` 四个字段（`refs/dump.cs` 的 TypeDefIndex 1203），没有挂自定义数据的余地。**但普通 mod 物品本来就同步**：消息 32 按物品编号走，两端同一套 mod、同一套发号（启动指纹已校验），对端 `SetDefaults` 认得的编号直接生效。不支持的只有"mod 物品的实例级附加数据进箱子"，那需要在 `ChestItem` 之外另开侧表+通道，目前没有真实需求。

### 4.2 玩家客户端状态（A3）

`GlobalPlayer` / 群落状态机那类「只算 `Main.myPlayer`」的数据，在多人下要看见别人就得走玩家同步。原版链路三段，`PlayerNetPipeline` 各接一段（`ModPlayer` 上对应 `SyncPlayer` / `CopyClientState` / `SendClientChanges` / `PlayerConnect` / `PlayerDisconnect`）：

| 时机 | 钩子 | 说明 |
|---|---|---|
| 进世界 / 任何人同步时 | `NetMessage.SyncOnePlayer` postfix | 原版把玩家数据发出去之后，作者借 `ModPacket` 发自己的那份 |
| 客户端每帧 | `Main.UpdateClient` 前后 + `Player.clientClone` postfix | 前半段：和上一帧的基线比对，变了就发（`SendClientChanges`）；原版跑完后：把当前状态重新复制进基线（`CopyClientState`） |
| 断线 | `NetMessage.SyncDisconnectedPlayer` 前置 | `PlayerDisconnect` 给最后一次清理机会，再交原版 |

基线是「本地玩家的 ModPlayer 实例数组」，用引用相等判断换人（同一槽位换人会重建实例）；断线时丢弃。

**不做服务端中继**：作者在 `SyncPlayer` / `SendClientChanges` 里发的包自己选 `ModPacket` 的目标（服务器或广播），管线只给时机不代发——代发就要替作者定义「哪些字段归谁」，这是 `GlobalPlayer` 的事，不是传输层的事。

## 5. 扩展方式

新加一种包：`KindXxx` 常量 + 发送侧的组装方法 + 接收侧一个 `ReceiveXxx`，然后在两个 switch 里各加一行。全局对象的编号表由安装期扫描自动生成，新增全局类不用改这里。

## 6. 与其它管线的边界

* **NPC / 弹幕管线**：本管线只搬 `SendExtraAI` 的字节；哪些字段要同步由作者决定。
* **配置管线**：配置的同步走本通道的一种包，但字段语义归配置管线。
* **物品管线**：原版消息（`SendData` 的 7/23/27 等）由本管线在前后补数据；物品的附属数据（通道 5）只搬作者声明的那串值，物品本身的字段归物品管线。
* **方块 / 墙壁管线**：同步只经过原版消息，本管线不介入。

## 7. 这一版没接

* **箱子里的自定义数据**：见对应小节 最后一段——箱子槽是 `ChestItem` 结构（4 个字段），装不下实例级附加数据；普通 mod 物品靠编号本来就同步。
* **物品的存档（`ModItem.SaveData` / `LoadData`）**：本版物品不落盘侧车数据，因此网络端也没有「用存档文本兜底」的那条退路；物品状态只走 `NetSend` / `NetReceive`。
* **压缩**：包体不压缩，超 65000 字节直接丢。
