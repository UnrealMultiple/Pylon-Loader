# 内容管线：网络（Net）

## 1. 职责

自建一条"Mod 数据"通道：把 `ModPacket`、`Mod.NetSend/NetReceive`、实体的 `SendExtraAI/ReceiveExtraAI`、全局对象的 `NetSend/NetReceive` 打包成带类型标记的二进制流，走游戏自己的 NetModule 消息；物品的实例级附加数据跟着原版物品包走——背包、地上、实例物品生成、箱子四个环节都不丢。

| 游戏时机 | 做什么 |
|---|---|
| `NetManager.Read` | 拦住我们的消息号 → 按标记分派（Mod 包 / 世界数据 / NPC 附加数据 / 弹幕附加数据 / 物品附属数据） |
| `NetMessage.SendData` | 每个 mod 的 `HijackSendData` 可否决原版发送；原版之前给物品包（5 = 装备/背包槽、21 = 地上物品、32 = 箱子槽、90 = 地上实例物品）补附属包；原版之后按消息号补发我们的数据（7 = 世界、23 = NPC、27 = 弹幕） |
| `MessageBuffer.ProcessData` | 原版把实体 / 槽位摆好之后，把对端的附属数据贴上去 |
| `InventoryStorage.SyncToChestItem / SyncFromChestItem / SyncFromChest` | 箱子槽与物品层互转的两端：存入抓取、取出贴回 |
| `Chest.Clear` | 世界重置时清空箱子侧表 |
| 安装期 | 建立"名称 → Mod"与"全局类型 → 编号"两张表 |

**不接**：数据包压缩、加密、重传；这些是游戏 NetModule 的职责。

## 2. 我们的设计

### 2.1 文件

```
Pipelines/Net/
  NetPipeline.cs   模块：两个游戏入口 + 各类包的收发与分派
  NetCodec.cs      值序列化（标记表）
  NetHandshake.cs  hello / welcome（前缀 pylon-cs:）
  ItemSync.cs      物品附属数据：组包（NetSend 值序列）、待贴队列、贴附
  ChestTable.cs    箱子槽侧表：物品层与精简槽两端的抓取 / 贴回
  NetReceiveHooks.cs  HijackGetData 的读取视图
  ContentFingerprint.cs  联机一致性指纹
```

### 2.2 通道：一个消息号 + 一个种类字节

消息号固定（`0xB17E`），首字节是种类，其次才是载荷。**先判种类再读内容**：

`KindPacket`（Mod 包）→ 名称 + 值序列；`KindWorld` → 名称 + 值序列；`KindNpc` / `KindProjectile` → 实体定位键 + 本体值序列 + 若干全局对象的值序列；物品附属数据（种类 5）→ 包号 + 位置 + 物品键 + 值序列。

### 2.3 包大小

硬上限 65000 字节：超过就丢并只报一次（`Safe.Once`）。不静默截断——截断的包在对端会读出错位的数据，比丢包更难查。

### 2.4 值序列化

一张固定的标记表（空值/整数族/浮点/布尔/字符串/布尔数组/二维向量），未知类型退化成 `ToString()` 当字符串发。接收端遇到未知标记返回 `null`，让上层按"缺值"处理——这样两侧协议版本不一致时是"少一个值"，而不是"整包错位"。

### 2.5 物品附属数据（通道种类 5）

原版物品包只把「编号 / 位置 / 堆叠 / 前缀」这类骨架字段摆上网：5 = 玩家装备 / 背包槽（玩家索引 + 槽号），21 = 地上物品，90 = 地上实例物品（两者定位的都是 `Main.item` 槽位，首字段同是两字节小端物品索引），作者写在 `ModItem.NetSend` 里的字段在哪个包型里都过不了网。做法（`ItemSync`）：

1. **发送侧**：`NetMessage.SendData` 里，物品包在调原版之前先补一条附属包。顺序不能反——接收侧是「等原版把物品摆好再贴」，晚到就贴不上。90 号包没有 32 号包那种"原版处理器内部转发"，照 21 的节奏先补后发即可。没重写 `NetSend` 的普通物品一个字节都不发。
2. **包体**：包号 + 位置（物品索引 / 玩家索引 + 槽号）+ 物品键（`Mod名/类型名`）+ 本体值序列 + 若干全局对象值序列（按全局注册表里的编号，不写类名字符串）。附属包里的包号跟随被补的原版包（5 / 21 / 32 / 90），对端按它路由贴附。
3. **接收侧**：挂在 `MessageBuffer.ProcessData` 上，先从包头取包号与位置（21 / 90 都取首字段的两字节小端索引；本构建原版对 21 / 90 共用同一段处理主体，两者包体形状一致，解析也共用一条分支），去待贴队列里找最早的一条，**原版处理完**再把附属数据贴到槽里那件物品上（那时物品才刚换成新的那件）。90 号包在客户端落地的两种情形——槽位已有物品的原地更新与空槽的重新生成——都发生在原版处理内部，处理完槽位里就是生成好的那件，贴附照常。
4. **校验**：贴之前比对物品键；对端编号指向另一件 mod 物品说明两端装载顺序不一致，丢掉这一条并只报一次。地上包（21 / 90）的物品索引还限定在 0..400——原版 `Main.item` 数组的实际范围——越界的附属包收下也贴不出去，直接丢弃，免得占住待贴队列的位置。
5. **进世界补发**：客户端进世界头 60 帧里原版会重发自己的背包，此时对端物品表还没铺好；这些槽号记下来，60 帧后按 `NetMessage.SendData(5, …)` 重发一次。这扇门罩住地上系包型（5 / 21 / 90）的发送侧，90 也不例外；箱子槽（32）走侧表自己的发送路径，不经这道门。

### 2.6 箱子槽（消息 32）与侧表

游戏的箱子槽是 `ChestItem` 结构（type / stack / prefix / favorited 四字段），装不下实例数据；完整 `Item` 只存在于箱子界面的 `InventoryStorage` 里，两侧靠 `SyncToChestItem`（物品层 → 精简槽）与 `SyncFromChestItem` / `SyncFromChest`（精简槽 → 物品层）互转。附属数据按 (箱子, 槽位) 记在 `ChestTable` 侧表里，在这两端各补一站：

* **存入**：`SyncToChestItem` 跑完之后，从物品层那件物品抓一遍 `NetSend` 值序列记入侧表；抓不到（普通物品、空槽）就撤条目。
* **发送**：消息 32 出网之前查侧表——槽里还是同一件物品（编号一致且没空）就随包补附属包（包号 32 + 箱子号 + 槽号 + 物品键 + 值序列）。没有条目就不发：**没有 mod 数据的箱子，32 号包与原版逐字节一致**。
* **接收**：附属包先记入侧表——必须赶在原版处理器跑之前，因为服务器对消息 32 的转发发生在原版处理器内部，条目晚了转发出去的箱子包就不带数据。原版写完槽位之后，把槽位展开成完整物品、贴上数据、刷新打开中的箱子界面（`InventoryStorage.SyncChestItemUpdateToStorage`）；没带附属包的原版 32（槽位清空 / 换了物品 / 对端没数据）同步撤本地条目。
* **开箱补发**：服务器应答开箱（`NetMessage.SendChestContentsTo`）时对每个槽位逐条发消息 32——侧表里有条目的槽随包带附属数据，任何一端打开箱子就补齐本地侧表，后进世界的端也不例外。
* **取出**：开箱（箱子界面创建，构造路径调 `SyncFromChest`）与槽位刷新时，把侧表里的值贴回展开出的物品；物品进背包之后走普通物品包路径（5 / 21），数据跟着走。

侧表只认世界箱子（编号在 `Main.chest` 里且不是 `bankChest`）；银行槽的物品走玩家槽位路径（消息 5），不进侧表。

**存档边界**：侧表只在本次世界会话内有效。世界箱子存档不收 mod 物品数据——世界侧车只有 banners / npcs / rooms / tiles / walls / tileentities / headers 等节，没有箱子节（见「这一版没接」）；换世界 / 重进世界后箱子里的实例数据不存在，`Chest.Clear` 时侧表一并清空。玩家背包与银行槽里的 mod 物品走玩家侧车（items 节，按容器 + 槽位），不受这条边界影响。

### 2.7 玩家客户端状态

`GlobalPlayer` / 群落状态机那类「只算 `Main.myPlayer`」的数据，在多人下要看见别人就得走玩家同步。原版链路三段，`PlayerNetPipeline` 各接一段（`ModPlayer` 上对应 `SyncPlayer` / `CopyClientState` / `SendClientChanges` / `PlayerConnect` / `PlayerDisconnect`）：

| 时机 | 钩子 | 说明 |
|---|---|---|
| 进世界 / 任何人同步时 | `NetMessage.SyncOnePlayer` postfix | 原版把玩家数据发出去之后，作者借 `ModPacket` 发自己的那份 |
| 客户端每帧 | `Main.UpdateClient` 前后 + `Player.clientClone` postfix | 前半段：和上一帧的基线比对，变了就发（`SendClientChanges`）；原版跑完后：把当前状态重新复制进基线（`CopyClientState`） |
| 断线 | `NetMessage.SyncDisconnectedPlayer` 前置 | `PlayerDisconnect` 给最后一次清理机会，再交原版 |

基线是「本地玩家的 ModPlayer 实例数组」，用引用相等判断换人（同一槽位换人会重建实例）；断线时丢弃。

**不做服务端中继**：作者在 `SyncPlayer` / `SendClientChanges` 里发的包自己选 `ModPacket` 的目标（服务器或广播），管线只给时机不代发——代发就要替作者定义「哪些字段归谁」，这是 `GlobalPlayer` 的事，不是传输层的事。

## 3. 取舍理由

* **为什么不按每个 mod 一条消息号？** 消息号是全局资源；mod 数量不可预知，动态分配会和游戏的消息号空间打架。固定一个号 + 种类字节 + mod 名，是唯一不需要和内核协商的方案。
* **为什么 NPC / 弹幕要单独两种包？** 它们的接收端需要"先找到实体"（NPC 按 index+type，弹幕按 owner+spawner+index+generation）；用定位键而不是引用，才能在乱序/丢包后仍然自洽。
* **为什么弹幕定位键是四元组？** 弹幕会被回收复用；`owner + key.Spawner + key.Index + key.Generation` 是唯一能区分"同一槽位的新旧弹幕"的组合。只按 index 会把数据写到复用过槽位的新弹幕上。
* **为什么 `HijackSendData` 放发送入口而不是别处？** 它是作者唯一能"替游戏决定这条消息发不发"的位置；放在 `SendData` 之前，作者可以拦下任何一条原生消息。
* **为什么实例物品包（90）与地上物品包（21）共用一条附属包路径？** 两者定位的是同一个东西——`Main.item` 的槽位，包体首字段同是两字节小端索引，本构建的原版处理器对两者甚至共用同一段主体；对附属包来说差别只在包号一个字节，键校验、过期、贴附全部复用。分开处理只会多出两份一模一样的代码。
* **为什么箱子数据记 (箱子, 槽位) 而不是记在物品上？** 精简槽里没有可挂数据的地方，完整物品又是箱子界面自己建的临时对象，随开随建随扔；能稳定定位箱内一件物品的只有它的槽位。侧表条目都带编号校验：槽里的物品换了编号，条目即作废，不会把数据贴到后来者身上。
* **为什么附属包要在原版处理器之前记侧表？** 服务器收到客户端的箱子槽更新后，会在原版处理器内部直接转发给其它客户端；转发走的是同一条 `SendData` 入口。条目先就位，转发出的箱子包才带得上附属数据，第三端才能在同一拍拿到完整物品。地上物品包（21 / 90）没有这条内部转发，所以贴附可以照常规放在原版处理之后。
* **为什么取出时贴数据而不是发送时重抓？** `NetSend` 读的是物品自己的状态；精简槽展开出的物品是空白的，只有把侧表里的值先贴回去（`NetReceive` 同序读回），随后的 `NetSend` 才有东西可写。存入侧同理——抓取发生在物品还完整的最后一刻（物品层 → 精简槽的转换处）。

## 4. 失败语义

| 情况 | 行为 |
|---|---|
| 载荷超过 65000 字节 | 丢弃，只报一次 |
| Mod 名找不到 | 丢弃（对端少装了 mod，不是错误） |
| 接收某个全局对象抛错 | 记一条，继续下一个全局对象 |
| 物品附属包对不上号（编号指向另一件 mod 物品） | 丢弃这一条并撤掉已记的箱子条目，只报一次；贴错物品比不同步更难查 |
| 地上附属包（21 / 90）的物品索引超出 0..400 | 丢弃，不入待贴队列 |
| 附属包在原版物品包之前没到 | 过期（10 秒）后丢弃 |
| 箱子附属包指向的箱子 / 槽位无效 | 撤掉这条条目 |
| NPC / 弹幕定位失败 | 丢弃这一包 |
| 值序列化遇到未知标记 | 读成 `null`，由上层按缺值处理 |
| `HandlePacket` 抛错 | 记一条，不影响其它包 |
| 整个包解析抛错 | 记一条，**不**再交回原版（半读的流已经不可用） |

### 4.1 内容指纹（联机一致性）

配方 / 商店 / 掉落这些管线的编号都按「安装顺序」发号，两端 mod 集合或顺序不同就整片错位，而且错得无声。`ContentFingerprint` 在注册完成时把「种类 + 编号 + Mod名/类型名」按顺序折成一个 64 位哈希：

* 启动时记一条日志（有多少内容、指纹多少）；
* 服务器发世界数据（消息 7）时随包把指纹发给他；
* 客户端收到后比对，不一致就记一条错（带两端的十六进制值），再把自己的指纹回给服务器——两侧日志都能对上号；
* 只报错不断连接：玩家至少能从日志知道是哪一侧 mod 装错了，断不断由人判断。

指纹不参与任何游戏逻辑；哈希用 FNV-1a，只为了「发现不同」，不抗碰撞。

## 5. 扩展方式

新加一种包：`KindXxx` 常量 + 发送侧的组装方法 + 接收侧一个 `ReceiveXxx`，然后在两个 switch 里各加一行。全局对象的编号表由安装期扫描自动生成，新增全局类不用改这里。物品附属数据要覆盖新的原版包型时，在 `ItemSync` 的包型集合里加一个常量，再给 `ProcessData` 补上那个包头的位置解析——地上系包型（21 / 90）共用同一条解析分支，只有非「两字节小端索引」开头的包型（如 32）才需要另写。

## 6. 与其它管线的边界

* **NPC / 弹幕管线**：本管线只搬 `SendExtraAI` 的字节；哪些字段要同步由作者决定。
* **配置管线**：配置的同步走本通道的一种包，但字段语义归配置管线。
* **物品管线**：原版消息（`SendData` 的 7/23/27 等）由本管线在前后补数据；物品的附属数据（通道 5）只搬作者声明的那串值，物品本身的字段归物品管线。
* **存档管线**：玩家容器里的 mod 物品由物品存档管线落玩家侧车；世界箱子里的实例数据两侧互不知晓——本管线只在会话内承接，存档管线的覆盖范围（见「这一版没接」）不因箱子同步的存在而改变。
* **方块 / 墙壁管线**：同步只经过原版消息，本管线不介入。

### 这一版没接

1. ~~**箱子里的自定义数据**~~：**已接（联机）**——箱子槽（消息 32）的实例数据由 `ChestTable` 侧表承接，随包照发（见 2.6）；没有 mod 数据的箱子，32 号包与原版逐字节一致。**边界**：侧表只在会话内有效——世界箱子存档不收 mod 物品数据（世界侧车没有箱子节），重进世界后数据不存在；绕过物品层直接写箱子槽的路径（机关沉积等）不经存取两端，不在覆盖范围。
2. **「只写 `SaveData`」物品的联机兜底**：玩家背包 / 银行的 mod 物品由物品存档管线按 `SaveData` / `LoadData` 落玩家侧车，但联机同步只走 `NetSend` / `NetReceive`（背包、地上、实例物品、箱子四条包型路径都一样）——没写 `NetSend` 的物品联机时状态不随包走，也没有「把存档文本随包兜底」的那条退路。
3. **压缩**：包体不压缩，超 65000 字节直接丢。
