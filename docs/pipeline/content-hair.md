# 内容管线：发型（Hair）

## 1. 职责

| 游戏时机 | 分派的作者数据 |
|---|---|
| 安装期（`Layout`，游戏表就绪之后） | 发号：`Type = 原版表长 + 注册序`，`DrawBackHair` 真值表随发号扩容 |
| 安装期（`Layout`，扩表步骤） | 两张贴图表（主贴图 / 戴帽子版）随号段扩到位（early 表请求，内容装配前必须扩好） |
| 安装期（`Static`） | `ModHair.SetStaticDefaults`（逐发型隔离）；戴帽子版贴图写槽（逐发型隔离） |
| 安装期（`Surface`） | 主贴图写槽（「写贴图与文本」步骤按 `TexturePath` 统一写入） |
| 表维护（运行期） | 游戏重建贴图表后随巡检重扩两张表，主贴图槽随重建回调重写 |
| 发型菜单（创建角色 / 理发师） | 两段式：`ListWarrantsRemake` 比对解锁态、`RebuildList` 把可用 mod 编号追加进可选列表 |
| 绘制（后发） | `Player.GetHairSettings` 后置：按 `HairIdTml.Sets.DrawBackHair` 回写 `backHairDraw` |
| 存档 / 读档 | mod 发型按 `Mod/类名` 记 sidecar（`pylon:hair`），原版存档文件里只落临时编号 0，读档时按名字找回 |
| 联机（原版玩家信息发完） | 该玩家是 mod 发型就补发一条同步包（玩家索引 + 发型号） |
| 联机（收到同步包） | 客户端贴到目标玩家；服务器改写来源索引后全网转发，未注册编号拒收 |

**不接**：发型菜单自己的滚动与分页、`GUIHairWindow` 的绘制、染发色（消费端在水管线）、跨端编号映射（按注册序裸传，见 2.6）。

## 2. 我们的设计

### 2.1 两个文件

`Pipelines/Hair/` 下：`HairTable.cs`（编号侧表：原版表长捕获、幂等发号、按键与按名反查；同文件的 `HairTables` 声明两张贴图表的扫描白名单与锚点）、`HairPipeline.cs`（安装门 + 扩表 + 静态默认值 + 写槽 + 菜单两段式 + 后发开关 + 存读档 + 多人同步）。

### 2.2 编号与两张贴图表

游戏没有编译期的发型总数，所以起点在**扩表之前**按 `TextureAssets.PlayerHair.Length` 捕获一次（`HairTable.Base`，读到 0 不缓存）。发号在「内容发号」步骤（`HairTable.Assign`）统一跑：幂等，只处理未注册的发型，游戏表还没建好（`Base` 取不到）就本轮不发号、下轮再来；发号的同时把 `HairIdTml.Sets.DrawBackHair` 扩到 `Type + 1`。

两张按类型索引的原生贴图表随号段扩容：`TextureAssets.PlayerHair`（主贴图）与 `PlayerHairAlt`（戴帽子版），走框架 `TableMaintenance`：管线声明两条 early 的 `TableRequest`（目标 `HairTable.Total`），「扩表」步骤在内容装配前一次扩到位，`Build` 里再 `Ensure` 一次兜底（幂等）。两张表都在 `TextureAssets` 一个类里，该类里同长度的数组太多、长度判据拦不全，所以各用白名单点名自己的字段。原版表长各自锚定：主表锚点即 `HairTable.Base`；alt 表按 `PlayerHairAlt.Length` 另行捕获（同为读到 0 不缓存），不假设两表等长。游戏重建贴图表（切语言 / 重载资源）后，「表维护」的周期巡检把两张表重扩到目标长度，mod 编号不越界；主贴图槽随重建回调（`InstallSteps.WriteTextures`，按 `TableFor(ModHair)` 找表）重写。

### 2.3 主贴图与戴帽子版

`TextureAssets.PlayerHair[type]` 写作者给的主贴图（`TexturePath`，默认 `assets/hairs/<Name>.png`，安装期「写贴图与文本」步骤统一写入）；`PlayerHairAlt[type]` 写 `AltTexture` 指的那张（默认同目录 `<Name>_Alt.png`，先探测，缺文件就退回主贴图）。两条路径各自加载、各自写槽，所以"戴帽子时发型消失"不会发生；主贴图缺失则该编号的槽留空（画出来空，不崩）。

### 2.4 装配逐发型隔离

`Build` 的两段装配各自逐发型兜异常：`SetStaticDefaults` 抛错记一条（按「来源 + 异常类型」首报去重）后继续下一个发型；戴帽子版贴图的路径探测、加载与写槽同样逐发型兜异常。坏一个发型只丢它自己的静态默认值与帽下发，其余发型的静态默认值、全部发型的两张贴图槽照常。

### 2.5 菜单两段式与存档按名字

菜单挂 `HairstyleUnlocksHelper` 的两个钩子：`ListWarrantsRemake` 用一份按编号缓存的解锁态比对变化，变了才要求重造列表（避免每帧重建）；`RebuildList` 在游戏算完的列表后面把可用 mod 编号追加进去。可用性判定分两处：创建角色看 `AvailableDuringCharacterCreation`，理发师看 `GetUnlockConditions` 的 `IsMet`；逐项包异常上报告警，坏一个不拖累其余。

存档挂 `Player.InternalSavePlayerFile` / `Player.LoadPlayer`：保存时先把 mod 发型临时换成 0 再走原版序列化，然后把 `Mod/类名` 写进 sidecar 键 `pylon:hair`；读档时按这个名字反查编号（先精确、再裸类名，重名当没有）写回 `player.hair`。卸掉 mod 后名字查不到，发型落回原版存档里的 0。

### 2.6 多人同步（玩家信息包后的附带包）

有 mod 发型注册时，通过 `NetPipeline.OpenChannel` 注册一个专属通道，并在 `NetMessage.SendData` 后置挂钩：

* **发送**：原版玩家信息（msgType 4）发完后，看该玩家的 `player.hair` 是不是本端已注册的 mod 发型，是就补发一条同步包。载荷两个字段：玩家索引（byte）、发型号（int32）。收发方向直接沿用原包的 `toClient` / `ignoreClient`——客户端上报自己的发型、服务器向每个收到玩家信息的客户端补一条，都不用自己维护名单。单人（netMode 0）在发送入口直接退出，零网络行为。
* **接收**：服务器先把来源索引改写成发包连接对应的玩家槽位（信任连接，不信载荷——玩家只能同步自己的发型），再校验编号：必须落在本端已注册的 mod 发型区间（`HairTable.Of` 非空），索引 0–254。校验通过就贴到 `Main.player[index].hair`，绘制与后发开关按字段现值自己生效；客户端到此结束，服务器再以改写后的索引全网转发一条（排除来源）。
* **拒收**：编号未注册（对端没装同一 mod、或该编号本端不存在）的包不贴、不转发，该玩家保留原版玩家信息带过来的值，也不会向其他客户端扩散。
* **裸传**：包里只传数字编号，不带 mod 名或发型名映射。两端都装同一 mod 且注册序一致时编号天然对齐；"是不是本端注册过的编号"是唯一校验，两边是不是同一个发型不做比对。内容不一致本来有指纹比对兜底告警（见 net 管线）。

## 3. 取舍理由

* **为什么发号等游戏表建好？** 编号的起点是原版表长，表没建出来就发号等于拍一个假起点；发号幂等且每轮重跑，晚一轮没有代价。
* **为什么两张贴图表进表维护而不是安装期直扩一次？** 直扩只覆盖安装期那一轮，游戏重建后没人补；进 `TableMaintenance` 后装配前扩到位、重建后巡检重扩，与其它随号段变长的表共用同一张安全网。
* **为什么贴图表用白名单点名字段？** `TableGrower` 的判据是"当前长度等于原版长度"，`TextureAssets` 里同长度的数组太多（其它贴图表管线撞过车）；两个表名唯一，点名最省也不会误伤。
* **为什么两张表各自锚定？** alt 表的原版表长没有可核实的编译期事实，单独按表读、读到 0 不缓存，不把「两表等长」当前提；主表复用发号锚点 `HairTable.Base`，一份事实两处消费。
* **为什么逐发型兜异常而不是整段失败？** 一个 mod 的坏发型不该决定别的 mod 能不能用发型；异常按来源去重上报，排障信息不丢。
* **为什么菜单用缓存比对而不是每帧重算？** `ListWarrantsRemake` 每帧都可能被问，只在解锁态变化时才要求重造列表，避免每帧重建。
* **为什么 alt 的加载与主贴图分开？** 见 2.3：alt 是第二条贴图路径（另加载文件、另写一张表），走同一套写槽设施但取值不同。
* **为什么编号不从 0 开始、也不用负号？** 负号在游戏里是"无发型/光头"这类特例的惯用表示，占用负区间会和原版语义打架；从原版表长之后接是最不容易误解的区间。
* **为什么同步包挂在玩家信息后面？** 玩家加入时原版必发一次玩家信息（客户端上报一次、服务器向其他客户端各广播一次），跟着这条消息补发就能覆盖所有发型需要被对齐的时机；方向沿用原包，逻辑里没有"该发给谁"的名单要维护。
* **为什么服务器要改写来源索引？** 载荷里的玩家索引可伪造；按收到包的连接改写之后，一个客户端改不了别人的发型。
* **为什么拒收而不回退成别的发型？** 收到未注册编号说明两端内容不一致；贴一个本端没有的数字只会越界或错位，拒收让对端保留原版通道带过来的值，损失最小且可预期。
* **为什么不做跨端映射？** 映射需要两端交换内容清单并对齐语义，超出本版通道的范围；两端 mod 集一致时裸传天然对齐，不一致时拒收兜底，指纹比对会先告警。
* **为什么私有字段能直读？** interop 的代理类型是按内存布局生成的，字段可见性不参与——游戏源码里的 private 字段在托管侧就是普通字段（编译期已验证）。这条结论对所有"私有字段读不到"的判断都适用。

## 4. 失败语义

| 情况 | 游戏侧表现 |
|---|---|
| 原版表长捕获不到（表还没建） | 不发号、不扩表，本轮什么都不做，下一轮再来 |
| 作者主贴图缺失 | 该编号的槽留空：画到它时什么都不显示（不崩） |
| 作者 `_Alt` 缺失 | 回退主贴图，戴帽子时发型不消失 |
| 安装流程重入（`Build` 再跑一次） | 发号幂等：已注册的跳过；扩表幂等：已到位的表不再动 |
| `SetStaticDefaults` 抛异常 | 记一条（按来源 + 异常类型首报去重）后继续：其余发型的静态默认值与全部戴帽子版贴图照常 |
| 戴帽子版贴图路径抛异常 | 记一条后继续：只丢该发型的帽下发 |
| 游戏重建贴图表（切语言 / 重载资源） | 表维护巡检重扩两张表；主贴图槽随重建回调重写；alt 槽重建后为空槽，戴帽子时该发型的帽下发不画（主发型照常） |
| `player.hair` 被设成 mod 编号 | 正常显示（两张表已扩长并写过槽） |
| 编号超出扩表目标长度（作者拿去乱算） | 绘制时按游戏自己的行为走（越界由游戏报），本管线不做额外保护 |
| 收到发型号未注册的同步包 | 拒收：不贴、不转发，该玩家保留原版玩家信息带过来的发型值 |
| 同步包里玩家索引不在 0–254 | 拒收 |
| 服务器收到合法同步包 | 以连接来源改写索引后贴并全网转发；转发同样走白名单，未注册编号不会扩散 |
| 单人游戏 | 有 mod 发型才装钩子，发送入口按 netMode 退出；没有网络读包，同步链路全程不触发 |

## 5. 扩展方式

菜单与戴帽子版已接，扩展的新入口都落在现有两段式与写槽设施上：

* **染色**（`player.hairDye`）：要在绘制链上拦染色值，本管线目前不参与；
* **alt 槽重建重写**：把戴帽子版写槽挂进重建回调（与主贴图槽同待遇）；
* **跨端映射**：同步包升级成带内容清单的对齐协议，替代裸传——通道注册面已经就位，只需扩展载荷。

## 6. 与其它管线的边界

* **玩家管线**：`player.hair` 这些字段归玩家侧数据；本管线只在存读档与网络同步两处写这一个字段，不碰玩家别的状态。
* **贴图设施**：写槽走 `TextureSlots` / `TextureTable.PlayerHair(/PlayerHairAlt)`；扩表与重建跟随归框架 `TableMaintenance`（表声明与锚点在 `HairTables`，管线声明请求、框架统一执行），本管线只调用。
* **net 管线**：通道注册、组帧与收包分发归 `NetPipeline`（`OpenChannel` / `SendChannel` / `Read`），本管线只注册自己的 kind 与两字段载荷；与物品附属数据、握手、指纹各走各的通道，互不掺和。
* **水管线**：染发色（`GetHairColor`）的消费端在水管线的群落染发色，本管线不参与。
* **NPC 头像**：`NpcHeadHooks` 独立分表（`NpcHead` / `NpcHeadBoss`），与发型编号互不占用；镇民头像的加载与发型无关。

### 这一版没接

1. **发型菜单的滚动与分页**：mod 发型已经会进创建角色与理发师的可选列表（按 `AvailableDuringCharacterCreation` / `GetUnlockConditions` 判定，两段式见 2.5），但菜单自己的滚动/每页数量是游戏算的。
2. **`GUIHairWindow` 的绘制**：不挂。
3. **染色**（`player.hairDye`）：照游戏的染色走，本管线不参与；群落染发色归水管线。
4. **跨端编号映射**：同步包只传数字编号（注册序裸传，见 2.6），不传 mod 名/发型名；两端内容不一致时靠拒收兜底，不做主动对齐。
5. **alt 槽重建重写**：重建后戴帽子版表随巡检重扩、但槽不重写（见 4）；主贴图槽已随重建回调重写。

### 对作者 API 的影响

| 变更 | 说明 |
|---|---|
| 语义明确 | 编号由管线分配（原版表长起、注册序），作者不要自己写死 |
| 生效 | 单个发型的 `SetStaticDefaults` 抛错只影响自己：其余发型与两张贴图表照常，异常按来源去重上报 |
| 生效 | `AltTexture` 写进 `PlayerHairAlt`（没有 `_Alt` 就用主贴图） |
| 生效 | `AvailableDuringCharacterCreation` / `GetUnlockConditions` 在菜单两段式里被调用 |
| 生效 | 多人同步自动接：两端都装同一 mod 时发型一致；对端没装则拒收，保留原版玩家信息带过来的值；作者不需要写任何网络代码 |
| 生效 | 存档按 `Mod/类名` 记 sidecar，卸 mod 后落回默认 |
| 生效 | 贴图表随号段扩容并纳入表维护：装配前扩到位，游戏重建后自动补扩，mod 发型不丢 |
| 本版不接 | 菜单滚动分页、`GUIHairWindow` 绘制、染色、跨端编号映射、alt 槽重建重写 |
